## Visão do produto

**Forja** é uma linha de montagem de software customizável que roda na máquina do desenvolvedor. O usuário
cadastra um projeto (um repositório git), desenha no canvas o fluxo de agentes de IA que transforma issues em
código revisado e PRs, e acompanha a execução ao vivo no próprio desenho.

- **O fluxo visual é o produto.** Cada nó é um prompt que roda em **contexto limpo** (um processo novo do
  Claude Code dentro de um container Docker), com entradas e saídas tipadas. O usuário cria nós, liga portas,
  agrupa nós em **loop** (repetir até uma condição, com teto) ou em **map** (rodar para cada item com
  concorrência limitada) e edita prompt, modelo, effort e ferramentas de cada nó direto no canvas.
- **Execução ao vivo no canvas**: qual nó está rodando, para qual issue, quantos na fila, quanto custou;
  clique no nó → logs em streaming.
- **Board** dos itens de trabalho cujas colunas são as etapas do fluxo — o card anda sozinho.
- **AFK de verdade**: gatilhos por cron, por evento e por coluna do board; quando o limite de uso do Claude
  é atingido, a execução pausa e retoma sozinha quando o limite reseta.
- **Local-first**: servidor Node no host + interface no navegador, armazenamento próprio em SQLite.

O fluxo de referência (template padrão, tem que funcionar no MVP):

```
[gatilho manual] → [source: issues com label Sandcastle]
   → map(TL: escreve a spec, concorrência 1) → map(Dev, concorrência 3)
   → map(Reviewer + git: PR, concorrência 1) → [output]
```

Um TL especifica uma issue por vez; três issues são desenvolvidas em paralelo; a revisão consome uma por vez, à
medida que cada Dev termina.

A especificação viva do pipeline que a Forja substitui é o `.sandcastle/main.mts` deste repositório (copiado
de `auto-development`): sync → plan → implement → review → rebase → evidence → PR, guarda de limite de uso e
retentativas. Ele vira o template "Pipeline Sandcastle" (#{GIT-05}).

## Nome e posicionamento

**Forja** — onde o software é forjado; curto, português, verbo e lugar ao mesmo tempo. CLI `forja`, diretório
de dados `~/.forja`.

Alternativas consideradas: **Esteira** (linha de montagem contínua; mais literal), **Tear** (tecer fluxos),
**Montadora** (fábrica, mais pesado), **Linha** (genérico demais).

Checagem de conflito (2026-11-03): o nome `forja` no npm está **retido pelo próprio npm** (pacote removido) —
publicar como pacote com escopo — decidido em 2026-11-13: **`@wellingtonfks/forja`** (escopo do usuário npm do
autor; #{HUM-01}). No GitHub há homônimos, o mais
próximo `nandomoreirame/forja` ("GUI client for vibe coders", 12 estrelas); há também o ForgeAI (fábrica de
software autônoma, em português, sem tração). Nenhum impede o uso local; marca registrada não verificada.

Posicionamento: **o Sandcastle é uma biblioteca para quem escreve o pipeline em código, o Paperclip tem o board, os
canvases existentes desenham — a Forja mostra, edita e opera a linha de montagem inteira, com motor e runtime próprios.**

## Benchmark e oportunidades

Resumo de [`docs/pesquisa/benchmark.md`](../pesquisa/benchmark.md) (13 sistemas, 2026-11-03):

- **Obrigatório no mercado**: fluxo visual, execução ao vivo no grafo, logs por etapa, gates humanos, cron,
  modelo/effort por etapa, GitHub Issues → PR, credenciais na UI, fluxo exportável.
- **Lacunas que ninguém resolve bem** e viram o nosso diferencial: concorrência limitada **visível** (map ×N
  com fila), loop com condição e teto e **custo por iteração**, **board derivado do fluxo**, **retomada
  automática após limite de uso**.
- **Diferenciais secundários** que entram no MVP: contexto limpo por nó com portas tipadas, Docker por nó,
  orçamento por run/nó, perfis de ferramentas (CodeGraph/MCP) por nó, Windows nativo, ver entrada/saída de
  cada nó e repetir um NodeRun (inspirado no n8n).
- **Decisão de arquitetura: motor e runtime próprios.** A Forja não depende de biblioteca de orquestração de terceiros:
  o motor (scheduler, map, loop, retentativas, orçamento, pausa por limite) e o runtime (git worktree + container Docker
  por item + adaptador do `claude -p --output-format stream-json`) são código da Forja, atrás da interface `AgentRuntime`.
  Isso permite mudar o funcionamento no futuro (outro isolamento, reaproveitar containers, outro harness como Codex ou o
  Agent SDK, execução remota) e acrescentar recursos sem esperar um projeto externo. O Sandcastle serviu de referência de
  desenho (workspace por branch, iterações com sinal de conclusão, comandos de contexto no prompt) e continua sendo usado
  só pelo pipeline que desenvolve a Forja (`.sandcastle/`).
- **Fora do MVP, deliberadamente**: IA que ajusta o fluxo (Planner/Director do RondoFlow), agentes conversando
  entre si (agent teams), app desktop, multiusuário, outros harnesses.

## Público e personas

- **Dev solo AFK** (persona principal; o autor): deixa a fábrica rodando à noite com 3 agentes, quer acordar
  com PRs prontos, saber o que travou e quanto custou. Usa Windows.
- **TL que desenha o fluxo**: ajusta prompts, troca modelo/effort do revisor, acrescenta um loop de testes;
  quer comparar versões do fluxo.
- **Revisor de PRs**: só aprova gates e PRs; quer evidência clara e rápida.

## Modelo de execução

Esta seção é a referência para todo o código de motor, runtime, canvas e board.

### Grafo

```ts
type PortType = "text" | "json" | "workItem" | "workItemList" | "branch" | "prUrl" | "any";
interface Port {
    name: string;
    type: PortType;
    required: boolean;
    schema?: JsonSchema;
}
interface FlowNode {
    id: string;
    type: NodeType;
    label: string;
    position: { x: number; y: number };
    parentGroupId?: string;
    inputs: Port[];
    outputs: Port[];
    config: NodeConfig;
}
interface FlowEdge {
    id: string;
    from: { nodeId: string; port: string };
    to: { nodeId: string; port: string };
}
interface FlowGroup {
    id: string;
    kind: "loop" | "map";
    label: string;
    parentGroupId?: string;
    position: { x: number; y: number };
    size: { width: number; height: number };
    config: LoopConfig | MapConfig;
}
interface MapConfig {
    concurrency: number;
    barrier: boolean;
    failFast: boolean;
}
interface LoopConfig {
    maxIterations: number;
    until: Condition;
    carry: string[];
}
```

Um grupo é ligado ao resto do grafo pelas arestas que cruzam sua borda: a aresta que entra em um nó do
grupo vinda de fora é uma entrada do grupo; a que sai é uma saída. Num `map`, a entrada do tipo
`workItemList` é a lista iterada e cada execução interna recebe um `workItem`.

Regras de validação (`src/engine/graph_validation.ts`): portas obrigatórias ligadas; tipos compatíveis
(`any` aceita tudo; `workItem` → `workItemList` só via map); **ciclos só dentro de grupos loop**; grupos
aninham sem sobreposição parcial; `concurrency ≥ 1`; `maxIterations` entre 1 e 50; variáveis de prompt
existem; exatamente um `trigger`.

### Itens como fichas

O `trigger` inicia a run com zero ou mais itens; o `source` busca itens (GitHub/local). Cada nó executa
**por item**: um `NodeRun` começa quando todas as entradas obrigatórias daquele item estão disponíveis.
Nós fora de grupos que recebem uma lista (`workItemList`) executam uma vez para a lista.

### Map (concorrência)

Executa o subgrafo uma vez por item, com no máximo `concurrency` itens ao mesmo tempo; os demais ficam em
fila visível (FIFO). Saída: lista na ordem de entrada. **Streaming por padrão**: cada item concluído segue
imediatamente a jusante (o Reviewer começa no primeiro Dev pronto); `barrier: true` espera todos. Falha de um
item não para os outros, salvo `failFast`. Lista vazia conclui com `[]`.

Dentro de um map, **o item atual é implícito**: todo nó interno tem acesso a `{{item.*}}` e ao workspace do item
sem precisar de aresta. Um map recebe sua lista por uma aresta `workItemList` que cruza a borda **ou** por arestas
vindas de nós de outro map (maps encadeados): nesse caso as arestas são **correlacionadas por item** — a saída do
TL para a issue 42 chega ao Dev da issue 42 — e o map a jusante itera sobre os itens que concluíram o anterior
(streaming). Itens que falharam no map anterior não seguem.

### Loop

Executa o subgrafo; avalia `until` sobre as saídas da iteração (ex.: `review.approved == true`, ou
`tests.exitCode == 0`); se falso e `iteration < maxIterations`, repete passando as portas `carry` (ex.:
comentários do revisor) para a próxima. Ao atingir o teto sai pela porta `exhausted`. **Todo loop tem teto.**

### Concorrência global

Além do `concurrency` do grupo há teto por projeto e global de NodeRuns de agente simultâneos (padrão 3) e
um intervalo mínimo entre inícios (padrão 5 s) para não estourar limites por minuto.

### Contexto limpo, workspace e saída

- Cada `NodeRun` de agente é um processo novo do `claude -p` (via `docker exec`): sem conversa herdada. Contexto = system
  prompt do projeto + prompt do nó renderizado com as entradas + arquivos do workspace + ferramentas do perfil.
- `workspace: "item"` (padrão): um **git worktree** do item em `~/.forja/worktrees/` montado num **container Docker
  por item** (`sleep infinity`; os nós rodam com `docker exec`), com o branch do item (`forja/issue-<número>` ou `forja/item-<id>`), compartilhado pelos nós daquele item ao longo
  da run (Dev escreve, Reviewer lê o mesmo branch). Fechado quando o item termina a run.
- `workspace: "none"`: nó de planejamento sem branch: container efêmero com o repositório montado **somente leitura**.
- **Iterações** (`maxIterations` + `completionSignal`): o runtime repete o agente em contexto limpo no mesmo workspace até o
  sinal aparecer (padrão "Ralph" do pipeline atual). `maxTurns` limita os turnos de cada execução (`--max-turns`).
- **Comandos de contexto**: `` !`git log --oneline -5` `` no prompt é executado no workspace e substituído pela saída antes do
  envio (`expandPromptCommands`, padrão ligado).
- Prompt é template com variáveis das portas: `{{inputs.spec}}`, `{{item.title}}`, `{{item.number}}`,
  `{{project.baseBranch}}`. Variável desconhecida é erro de validação.
- **Saída estruturada**: o nó declara `outputSchema` (JSON Schema); o runtime usa `Output.object({ tag:
"output", schema })` e o prompt recebe a instrução de terminar com `<output>{json}</output>`. Saída inválida →
  `FAILED` com a mensagem no log (conta como tentativa).

### Máquinas de estado

- `Run`: `QUEUED → RUNNING ⇄ PAUSED → SUCCEEDED | FAILED | CANCELED`; `pauseReason: "user" | "usage_limit" | "budget"`, `resumeAt?`.
- `NodeRun`: `PENDING → QUEUED → RUNNING → SUCCEEDED | FAILED | CANCELED | SKIPPED`, mais `WAITING_APPROVAL`,
  `WAITING_LIMIT` e `INTERRUPTED`. Falha com tentativas restantes cria novo `NodeRun` com `attempt + 1`.
- `FlowVersion`: `DRAFT → PUBLISHED → ARCHIVED`. Só publicada executa; **a run fica presa à versão**.
- Coluna do `WorkItem` no board: derivada do nó/grupo onde o item está na run ativa, mais `Backlog`,
  `Bloqueado`, `Precisa de humano` e `Concluído`.

Transições são funções puras (`canTransition`, `reduce`) em `src/engine/`.

### Limite de uso e orçamento

- O runtime reconhece mensagens de limite do Claude Code ("5-hour limit reached ∙ resets 3pm", "Weekly limit
  reached · resets Oct 24, 9am (America/Sao_Paulo)", "usage limit reached|<epoch>", 429/529) e lança
  `UsageLimitError { resetAt? }`. O motor põe o NodeRun em `WAITING_LIMIT` (não conta tentativa), pausa a run
  com `resumeAt = resetAt + margem` (padrão 5 min; sem horário: 30 min), emite `usage.limit_reached` e, ao
  chegar a hora, `usage.limit_reset` e retoma. Lógica portada de `.sandcastle/usage_guard.mts`.
- Orçamento por run, por nó e por dia (tokens ou US$), avaliado **antes** de iniciar cada NodeRun; ao estourar:
  pausar (padrão), falhar ou pedir aprovação.

### Durabilidade

Estado persistido a cada transição. Ao subir, NodeRuns `RUNNING` viram `INTERRUPTED` e são reagendados como
nova tentativa (sem contar para o limite de tentativas); containers órfãos da Forja são encerrados.

## Escopo do MVP

**Entra**: projetos; credenciais; perfis de ferramentas; editor visual completo (nós, portas, grupos loop/map,
inspector com prompt/modelo/effort/ferramentas, validação, versões, templates, import/export); motor com map,

MCP; fork de execução com estado editado; comparação A/B de versões do fluxo; notificações do navegador;
keychain do SO.

## Direção de design

**Conceito: "oficina iluminada".** Uma forja é escura, quente e precisa: metal frio, brasa onde há trabalho.
A interface é calma e escura por padrão (o usuário passa horas olhando execuções), com **cor só onde há
atividade** — o nó em execução brilha como brasa; o resto é aço. Nada de neon, gradientes roxos de "IA" ou
glassmorphism. Tema claro existe (mesmos papéis de cor), mas o escuro é o padrão.

**Paleta (tema escuro; tokens em `src/web/styles/tokens.css`)**

| `--color-surface`        | `#1C1F24` | Painéis, cards, nós                             |
| `--color-surface-raised` | `#252930` | Drawer, popover, nó selecionado                 |

`accent #C2611F`. Contraste AA verificado para texto e componentes.

**Tipografia**: UI em **IBM Plex Sans** (400/500/600); logs, prompts e IDs em **JetBrains Mono** (400/500);
títulos de página em **IBM Plex Sans Condensed** 600. Escala: 12 / 13 (padrão da UI) / 14 / 16 / 20 / 24.
Fontes empacotadas localmente (`@fontsource`), sem CDN — o app funciona offline.

**Forma**: raio 6 px (componentes), 10 px (nós e cards), 14 px (drawers e diálogos). Bordas de 1 px em vez de
sombras; sombra só em elementos flutuantes (`0 8px 24px rgb(0 0 0 / .35)`). Espaçamento em base 4.

**Motion**: rápido e funcional (120–180 ms, `ease-out`). No canvas, só três coisas animam: o brilho do nó
rodando, o tracejado da aresta onde há dado fluindo e a entrada do card que muda de coluna no board. Tudo
respeita `prefers-reduced-motion`.

**Três superfícies**

- **Canvas** (editor e execução ao vivo): espacial, zoom de 25% a 200%; nó com cabeçalho (ícone do tipo,
  rótulo, badge de estado), corpo resumido (modelo + effort para agentes; comando para script) e portas
  rotuladas nas laterais. Grupos são molduras com rótulo no canto ("map ×3", "loop ≤5") e contadores ao vivo
  ("2 rodando · 1 na fila · 4 feitos"). Inspector à direita (360 px), paleta à esquerda (240 px). Abaixo de
  50% de zoom, os nós mostram só cabeçalho.
- **Logs** (drawer inferior ou tela cheia): monoespaçado 13 px, linha 1.5, fundo `--color-canvas`; eventos de
  ferramenta recolhíveis com o nome em destaque; erros com faixa vermelha à esquerda; timestamps relativos
  (`+00:42`); seguir o fim ligado por padrão e desligado ao rolar para cima.
- **Board e configurações**: listas e formulários densos e legíveis; colunas do board com largura fixa
  (300 px), cards com título, número da issue, etapa atual, mini badge de estado e custo acumulado.

**Tom de voz**: direto, técnico, em português, sem exclamações nem personificação ("Reviewer falhou na
tentativa 2/3: saída sem o bloco `<output>`", não "Ops! Algo deu errado 😅"). Botões com verbos: "Publicar
versão", "Repetir execução".

**Evitar**: visual de painel SaaS genérico (cards brancos com sombra em grid), neon/cyberpunk, mascotes,
"escritório virtual" com bonecos, emojis na UI, cor como única forma de informação.

## Regras de domínio fixas

- Run fixa a versão do fluxo; editar o fluxo nunca altera runs em andamento.
- Contexto limpo por nó; nada passa entre nós fora das portas e do workspace do item.
- Todo loop tem teto; todo nó de agente tem timeout total, timeout de inatividade e teto de iterações e de turnos.
- Concorrência sempre limitada (grupo, projeto, global).
- Um workspace (container + branch) por item; nunca dois itens no mesmo branch.
- O `source` não entrega itens bloqueados por issues abertas.
- Logs são append-only, ligados a NodeRun, com segredos mascarados antes de gravar.
- Nada destrutivo sem gate: push forçado e merge exigem nó `gate`; a Forja nunca mescla PR sozinha no MVP.
- Datas em UTC no banco; cron avaliado no fuso do projeto (padrão do SO).
- Auditoria (`audit_log`): publicar versão, mudar credencial, aprovar/rejeitar gate, cancelar run.

## Stack e arquitetura

**Decisão: app web local, não desktop.** Servidor Node no host + SPA no navegador, iniciado por `forja` (abre
o navegador). Uma base de código, sem empacotar/assinar instaladores; o servidor usa o Docker, o git e o `gh`
do host. **Docker é obrigatório** porque cada nó de agente roda em container (escolha do usuário). Desktop fica para o Pós-MVP como casca sobre a mesma SPA.

| Camada            | Escolha                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| Linguagem         | TypeScript `strict`, ESM, Node ≥ 22                                                                           |
| Servidor          | Fastify + `fastify-type-provider-zod` + `@fastify/static`                                                     |
| Tempo real        | SSE em `/api/events` com `Last-Event-ID`                                                                      |
| UI                | React 19 + Vite + React Router; TanStack Query; Zustand no editor                                             |
| Canvas            | `@xyflow/react` (React Flow) + `elkjs` (auto-layout)                                                          |
| Estilo / UI       | Tailwind CSS v4 + tokens CSS; Radix UI; ícones `lucide-react`                                                 |
| Editor de prompt  | CodeMirror 6                                                                                                  |
| Logs              | `@tanstack/react-virtual`                                                                                     |
| Validação         | Zod (v4) em todas as fronteiras; `z.toJSONSchema` para schemas de saída                                       |
| Banco             | SQLite (`better-sqlite3`, WAL) + Drizzle (query builder) + migrador próprio por domínio (SQL)                 |
| Logs brutos       | NDJSON por NodeRun em `~/.forja/logs/<runId>/<nodeRunId>.ndjson`                                              |
| Agendamento       | `croner`                                                                                                      |

Padrões: `src/engine` não importa I/O nem `Date.now()` (recebe `Clock`); rotas chamam services; services recebem
repositórios e providers por parâmetro; todo evento passa pelo `EventBus` tipado de `src/shared/events.ts`;
variáveis de ambiente só via `src/lib/env.ts`; integrações sempre com fake; processos sempre com timeout e
encerramento da árvore.

**Testabilidade no sandbox**: `npm run test` usa `FakeAgentRuntime`, `FakeClock`, SQLite `:memory:`,
`FakeCommandRunner`, `FakeGitProvider`, `FakeGitHubProvider`; o runtime Docker fala com `git` e `docker` só pelo
`CommandRunner`, então seus testes conferem os comandos montados e reproduzem fixtures de stream-json. Testes com Docker,
`git` real ou `claude` real são `*.integration.test.ts` (`npm run test:integration`, fora do CI padrão).

Scripts npm: `dev`, `build`, `start`, `lint`, `format`, `typecheck`, `test`, `test:watch`,
`test:integration`, `test:e2e`, mais o `sandcastle` já existente (pipeline de desenvolvimento, não usado pelo produto).

## Premissas e decisões em aberto

- **Monousuário local**, sem login (token de sessão local só para proteger a API de outros sites).
- **Fonte de itens**: issues do GitHub (via `gh`) e itens locais. Jira/Linear Pós-MVP.
- **Docker por nó desde o início** (escolha do usuário): exige Docker Desktop no Windows; sem Docker a Forja abre,
  edita fluxos e mostra o diagnóstico, mas não executa nós de agente.
- **Runtime próprio acoplado ao CLI do Claude Code**: mudanças de flags ou do formato stream-json afetam só `claude_command.ts`
  e `stream_json_parser.ts`; a versão mínima do CLI é registrada após #{HUM-03}.
- **Montagem do worktree no container**: o `.git` comum do repositório é montado no mesmo caminho absoluto; no Windows isso
  depende da tradução de caminhos do Docker Desktop (validar em #{HUM-03}).
- **Custo**: tokens vêm do `result` do CLI; o custo em US$ é recalculado com tabela de preços por modelo editável.
- **Nome do pacote npm** (`forja` está retido): decidir escopo em #{HUM-01}.
- A Forja nunca mescla PRs sozinha no MVP.
